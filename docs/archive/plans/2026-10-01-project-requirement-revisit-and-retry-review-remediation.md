# 项目需求重访与并发重试整改

> Status: archived
> Owner: frontend

## 背景与根因

上一轮只读复查发现两个边界。`app/assets/components/assets-workspace-client.tsx:985-1000,2108-2119` 用用户可见的相对时间文案标记“本次资料变更由显式需求读取负责”；同一分钟内时间文案不变时，自动 effect 没有运行，标记留到用户切走再返回该项目才被误消耗，跳过返回时本应执行的 GET。另一个边界在 `958-983,3095-3122`：请求代次会丢弃已过期的 GET 结果，但 `reloadCurrentRequirements` 仍把原始快照返回给重试处理器；重试期间若再次操作素材，旧请求可能触发与当前状态不符的成功提示。

## 涉及文件与具体改法

- `app/assets/components/assets-workspace-client.tsx`：记录上次需求 effect 对应的项目及认证作用域；只有同一项目因本次详情更新时间变化而重跑 effect，才消费并执行“跳过自动读取”。项目切换、登录作用域变化时清除旧跳过标记并正常读取。
- 同文件的需求读取返回 `{snapshot, applied}`；请求成功但已取消/代次过期时返回 `applied=false`。已过期的失败也不再冒充当前失败。抽屉重试只对真正应用的结果显示成功或无快照提示；当前请求失败仍准确保留错误与重试入口。其他调用方继续沿用既有读取与错误处理语义。
- `e2e/display-area.spec.ts`：补“同分钟资料变更→切换到另一项目→返回”的 GET 断言；补“需求重试 GET 挂起→再次操作素材→旧 GET 晚到”的反馈断言，验证旧结果不写回也不弹成功提示。
- 相邻 E2E 复测发现既有的旧需求读取竞态用例把共用素材留在“已移出”状态，造成最后的真实归档用例顺序运行时进入删除文案分支；该用例补资料成员状态恢复，保证共享种子在后续用例前一致。独立归档用例已通过，无需改产品文案。

后端 API、数据库、项目资料成员关系与视频链路不变。

## 风险与取舍

- 仍保留资料变更时的单次显式 GET；返回项目时新增的 GET 是用户切换后正常同步，不算重复读取。
- 不禁止重试期间管理素材；以请求代次判定结果是否仍有效，避免用户被旧请求误导。
- 相对时间文案仍只是现有列表展示字段，本次不把它扩展成服务端版本号；跳过条件增加项目/作用域边界，避免扩大改造范围。
