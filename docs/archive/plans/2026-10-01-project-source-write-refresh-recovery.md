# 项目资料写入后刷新失败的状态恢复

> Status: archived
> Owner: frontend
> Last verified: 2026-10-01

## 背景与根因

项目资料加入/移出接口在后端 `MultiMix-Backend/app/api/assets.py:1656,1705` 已提交事务，前端却把后续读取项目详情、需求快照与写入放在同一个错误边界：`app/assets/components/assets-workspace-client.tsx:2138-2160,3028-3041`。详情 GET 失败会被误报为“加入项目失败”或从 `project-resources-drawer.tsx:163-195` 显示“项目资源操作失败”，导致用户误以为要再次提交。旧详情仍可能留在抽屉或项目状态中。

## 范围与改法

1. 在 `app/assets/components/assets-workspace-client.tsx` 的两个项目资料入口，将 PUT/DELETE 的失败与后续 GET 的失败拆开：只有写入本身失败才显示写入失败；写入成功即关闭“加入项目”选择器或完成抽屉动作。后续读取失败只提示“已保存，资料暂未同步”，不误伤全局写入连接状态。
2. 项目详情刷新失败时把对应项目详情标记为未加载，失效过时详情请求；当前项目使用已有“重试加载”入口恢复，未选中项目在后续进入时重新加载。项目资料抽屉在当前项目详情无法验证时关闭，避免继续展示旧成员关系。
3. 需求快照读取单独处理；失败时清除该项目的旧缓存，提示需求理解暂未同步，但不把已提交的成员关系判为失败。下一次成功读取可以恢复。
4. 在 `e2e/display-area.spec.ts` 加入写入成功、后续详情/需求读取失败的隔离浏览器回归，确认提示、抽屉状态、重试恢复与无重复提交。保留现有成功路径测试。

不修改后端 API、数据契约、生产环境或与此无关的 E2E fixture 并发隔离建议。

## 风险与取舍

- 已保存但详情暂不可读时，暂时停用基于旧详情的操作，优先保证“已保存”事实和成员关系展示可信；恢复读取后恢复正常交互。
- 需求快照失效会暂时隐藏旧需求理解，避免将过时内容误认为最新；不主动重发写请求。
- 使用接口故障注入的浏览器测试，不触碰生产数据；一体化 E2E 使用一次性 SQLite，结束后清理。
