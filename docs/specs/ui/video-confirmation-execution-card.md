# 视频确认后的执行过程卡

> Status: current
> Owner: frontend
> Last verified: 2026-08-14

## 1. 目的

用户在编导稿方案卡上点击“确认，生成视频工程”后，原方案卡继续作为已确认的工作对象保留；系统在它下方新增一张独立执行过程卡，用真实任务状态解释视频工程正在发生什么。

本规范锁定以下体验：

- 原确认卡不能变形成执行卡；确认后只切换为紧凑的“已确认”状态。
- 点击确认不能在可见聊天流中伪造一条用户主动发送的确认气泡。
- 执行过程由独立卡片承载，位置紧随已确认方案之后。
- 执行卡统一使用用户语言“视频生成进度”，不向用户暴露“视频工程”这一内部实现概念；生成完成后直接提供编辑与导出能力。
- 执行中默认展示简洁的主步骤；完成后自动收起，用户可重新展开。
- 失败、重试、刷新和断线恢复都复用同一张执行卡，不新增平行任务卡。

当前可点击原型中的交互基准：

- 动态确认与执行过程：`docs/specs/ui/prototypes/current/screens/workspace-copy.html`
- 视频已确认和已完成状态：`docs/specs/ui/prototypes/current/screens/workspace-video.html`

## 2. 用户可见流程

```text
待确认方案卡
  -> 用户点击确认
  -> 方案卡切换为“已确认”
  -> 其下方出现独立执行卡
  -> 执行卡用真实 job 状态更新主步骤
  -> 视频工程 ready 后立即开放编辑入口
  -> 可选 MG overlay 继续后台执行
  -> 全部执行结束后自动收起为一行摘要
```

### 2.1 点击确认后的可见结果

点击后立即发生的视觉变化：

1. 原方案卡保留，按钮消失，右上角显示“已确认”。
2. 方案卡下方出现执行卡，初始状态为“正在创建视频工程任务”。
3. 不追加“确认，生成视频工程（横屏 16:9）”用户气泡。
4. 不追加“已确认，正在创建视频工程任务”普通助手文字。
5. 后端返回工程资产和 job 后，执行卡绑定真实 `asset_id` 与 `job_public_id`，开始轮询真实步骤。

### 2.2 工作卡宽度

确认卡和执行卡属于同一条“确认方案 -> 创建工程”链路，必须共享同一个工作卡宽度契约：

- 桌面端最大宽度为 `560px`，且两张卡在同一会话列中实际等宽。
- 窄屏下两张卡使用相同的可用宽度自动收缩，不能横向溢出。
- 宽度由共同的消息容器或共享布局变量控制，不能依赖卡片文案的固有宽度把卡片撑开。
- 产物入口卡可以沿用同一会话列宽度，但不作为确认卡和执行卡等宽的判定来源。
- 对话内的“内容生成进度”卡同样属于工作卡：停止、成功、失败等状态使用同一宽度契约，不能因文案较短而缩窄。

后端仍需持久化确认命令及排队消息。它们用于事务、幂等、审计和断线恢复，但前端应把共享同一 `confirmation_idempotency_key` 的这组消息识别为控制事件：

- `video_workflow_stage=director_script_confirmed` 的用户消息不渲染为用户气泡。
- `video_workflow_stage=video_project_queued` 的助手消息不重复渲染正文，只作为执行卡的持久化锚点。
- 刷新页面后，已确认方案卡和执行卡必须从服务端记录恢复，不能依赖本地临时状态。

## 3. 步骤模型

采用“固定流程骨架 + 真实任务动态分支”。

### 3.1 固定规则

- 每种执行类型由后端定义稳定的步骤代码、顺序和商家语言标签。
- LLM 不生成步骤数量、步骤名称或完成状态。
- 前端不使用定时器模拟进度，不按预计耗时自动推进。
- `status`、失败位置和耗时必须来自真实请求状态或后端 job 事件。
- 成功、停止和失败都必须保留此前真实发生的步骤，终态自动收起只隐藏详情，不能丢失过程历史或退化为单一终态步骤。
- 历史记录缺少进度事件时，只能从任务的持久化生命周期补回确定发生过的“已排队”和当前终态；不得据此推断或补写其他处理中步骤。
- 未获得真实事件时，只能显示固定流程骨架：`create_job` 为运行中，后续步骤均为等待；不得编造后续步骤已经开始或完成。

确认请求尚未返回时，前端可以展示固定的四步骨架，但只能把
`create_job` 标记为 `run`，其余三步必须为 `wait`。该骨架只表达稳定流程，
不表达后端已经推进；响应返回后必须立即由真实 job `steps[]` 整体接管。

### 3.2 视频工程主步骤

第一版默认只显示以下主步骤：

1. `create_job`：创建视频工程任务。
2. `prepare_scenes`：读取已确认方案并准备分镜。
3. `prepare_media`：匹配分镜素材并准备配音、字幕。
4. `build_project`：组装可编辑视频工程。

具体分镜数、素材命中数、公开素材兜底数和配音结果作为步骤摘要，不增加默认主步骤数量。例如：

- `准备 4 个分镜`
- `4 个分镜命中已保存素材`
- `1 个分镜使用公开素材兜底`
- `3 段配音已生成，1 段待重试`

当前后端通过 `VideoJobRead.steps[]` 返回产品语义步骤。普通用户 DTO 不返回内部
`render_stage`、`step_marks` 或 `elapsed_seconds`；已有编导稿应显示为“读取已确认方案并准备分镜”。

### 3.3 可选动态分支

以下内容只有存在真实任务时才出现，并默认折叠为主步骤下的详情：

- 已选公开素材的下载、验证与持久化。
- 分镜级配音生成。
- 分镜级 MG overlay 渲染。
- 断线后的状态恢复。

MG 是主工程 ready 后执行的异步增强步骤，但在产品状态上是完成门槛：

- 有 MG 计划时，执行卡显示“正在生成 MG 动效”；全部计划项成功前，视频保持“生成中”，不开放编辑或导出。
- 任一 overlay MG 失败或超时，视频进入失败态，显示分镜错误与重试入口；内部原主画面仅供恢复和诊断，不能作为完成的视频交付。
- full-frame `mg_scene` 失败时，工程使用已持久化的无文字空白画面保留该镜时长，并显示警告。
- 只有空白占位无法持久化、归属校验失败或主轨无法连续覆盖时，主生成任务才失败。
- 没有真实 MG job 状态时，不展示 MG 运行进度。

## 4. 执行卡状态

### 4.1 执行中

默认展开主步骤：

- 头部标题固定为 `视频生成进度`，不随执行中、完成或失败状态改变。
- 标题文字与上方“视频方案”的真实标题文字统一为 `12px`；不能只比较父容器字号，浏览器最终计算样式必须一致。
- 标题右侧状态点始终可见：全部完成为绿色、执行失败或未完成为红色、正在执行为黄色。
- 状态、步骤数和总耗时继续作为次级信息展示。
- 已完成：绿色对勾、实际耗时。
- 正在执行：渐变运行图标、当前步骤文案、静态或动画进度强调。
- 等待：空心圆、灰色文案。
- 子任务默认不展开，用户可以手动查看。

### 4.2 主工程已就绪、MG 仍在执行

主标题仍显示 `视频生成进度`，次级状态显示 `正在生成画面动效`。卡片保留展开状态；视频仍处于生成中，待全部计划的 MG 完成后才开放编辑与导出。

### 4.3 全部完成

完成后自动收起为单行摘要：

```text
✓ MultiMix 已完成 · 共 4 步 · 12.9s  ˅
```

规则：

- 自动收起只发生一次；用户手动展开后，本次页面会话内不再强制收起。
- 有真实总耗时时显示耗时；没有时只显示步骤数。
- 点击摘要可以展开全部主步骤和可用的子任务历史。
- 收起不删除数据，刷新后仍保持完成态并默认收起。

### 4.4 失败

失败时不自动收起：

- 已完成步骤继续显示完成状态。
- 失败步骤显示失败原因摘要。
- 未执行步骤保持等待状态。
- 卡片内提供“重试失败步骤”或“恢复任务”入口。
- “未提交”与“服务端任务失败”必须区分；前者允许重新确认，后者复用原工程和 job 重试。

失败状态使用统一的状态图标和信息层级：

- 头部、完成、运行、失败和等待状态共享同一个 `18px` 圆形状态槽；成功与失败均使用 SVG 图标，不能混用文本字符和 SVG。
- 头部与步骤行共享 `30px` 状态列，保证头部状态、步骤状态和正文起点处于相同垂直轴线。
- 等待状态使用完整 `18px` 圆环，不使用比成功、失败状态更小的独立圆点。
- 失败步骤本身承担默认失败状态，不在执行卡底部重复显示“视频工程生成失败，请重试”。
- 普通执行卡只显示服务端投影后的用户可读错误；原始错误和技术诊断仅进入受保护的
  pilot/admin 路径，不能进入普通用户响应或折叠详情。
- 普通执行卡不展示服务端原始计时；需要耗时排障时走受保护的诊断路径。
- 重试按钮使用明确动作“重新执行此步骤”，并继续复用原工程和 job。

## 5. 数据与组件边界

### 5.1 后端权威数据

- 确认事务：`client_request_id`、`confirmation_idempotency_key`。
- 工程绑定：`asset_id`、`latest_job_public_id`。
- 普通用户主状态：公开 `status`、`workflow_stage`、`steps[]`。
- 服务端内部可继续使用 `VideoRenderJob.render_stage` 与 `result_payload.step_marks` 派生公开步骤，
  但它们不进入普通用户 DTO 或 OpenAPI。
- 工程 readiness：统一的 `video_project` readiness predicate。
- MG：分镜级 `mg_decision` 和真实 MG jobs。

### 5.2 前端职责

- `ConfirmCard` 只负责待确认与已确认两态。
- `AgentRunTimeline` 只负责执行状态，不承接确认卡内容。
- `ConversationStudio` 负责将确认控制事件折叠为“已确认方案 + 执行卡”，隐藏自动确认气泡和重复助手正文。
- `AssetsWorkspaceClient` 继续轮询真实 job，并按工程资产 ID 提供执行步骤。
- `asset-mappers` 负责把后端步骤代码映射成稳定的商家语言；未知步骤使用安全通用文案，不暴露内部模型或工具名。

执行卡需要持久化锚点，不能只依赖 `confirmingPlanKey`。网络响应丢失时，前端使用同一个 `client_request_id` 对账；找到服务端消息后恢复同一张执行卡，未找到时显示“未提交”。

### 5.3 确认路由

确认卡发出的明确编导稿确认指令是确定性命令。后端在已经解析出当前会话和选中编导稿后，必须在 Agent preflight 的入口处直接短路，不能进入意图解释、LLM 调用或生成循环。该短路可以保留在 preflight 的终态工作流门禁中，不要求复制一套平行确认路由。

- 明确确认仍必须执行对象归属、编导稿类型和质量门校验。
- 直接路由不能绕过事务、语义幂等、持久化消息或后台 job 派发规则。
- “开始吧”等需要上下文判断的模糊表达继续保留现有 Agent 路由，不因短路门禁而扩大确认语义。
- 前端不能因为快速路径存在而假设请求成功；只有持久化响应或 `client_request_id` 对账结果可以把乐观状态替换为真实状态。

### 5.4 失败状态一致性

- 主视频 job 进入 `failed/stale` 时，执行卡和产物卡必须在同一次服务端对账后共同显示失败，不能出现“执行失败 / 视频生成中”的冲突。
- 前端映射必须让已持久化的 `asset.status=failed` 优先于残留的 `metadata.orchestration_pending=true`，作为旧数据和竞态的防御。
- MG 子 job 失败或超时会使视频产物显示失败；主工程继续保留以便重试和诊断，产物卡不开放编辑或导出。

## 6. 无障碍与动效

- 卡片头部是可操作按钮，使用 `aria-expanded` 表达展开状态。
- 执行中区域使用 `aria-live=polite`，只在步骤发生变化时播报。
- 自动收起不能抢走键盘焦点。
- `prefers-reduced-motion: reduce` 下关闭呼吸和 shimmer 动画，状态仍通过图标与文案可辨认。
- 失败、等待、完成不能只依赖颜色区分。

## 7. 验证案例

### 7.1 正常确认

- [ ] 点击确认后，原方案卡显示“已确认”。
- [ ] 不出现自动用户确认气泡。
- [ ] 不出现重复的排队助手正文。
- [ ] 方案卡下方出现独立执行卡。
- [ ] 执行卡标题显示“视频生成进度”，不显示“MultiMix 执行”或“视频工程生成进度”。
- [ ] “视频生成进度”与上方“视频方案”的最终计算字号均为 `12px`。
- [ ] 执行卡状态点按整体状态显示：完成绿色、失败或未完成红色、执行中黄色。
- [ ] 确认卡和执行卡在桌面端实际等宽，窄屏下同步收缩且不溢出。
- [ ] 确认请求返回前显示“第 1 步 / 共 4 步”，后三步均为等待状态。
- [ ] 执行卡从真实 job `steps[]` 更新状态和耗时。
- [ ] 明确确认指令在 Agent preflight 入口直接短路，不调用意图解释或 LLM；模糊上下文指令仍保留原路由。
- [ ] 全部完成后自动收起，点击后可展开历史步骤。

### 7.2 刷新与断线

- [ ] 任务执行中刷新页面，已确认方案和同一张执行卡恢复。
- [ ] 请求响应丢失但服务端已提交时，通过 `client_request_id` 恢复任务。
- [ ] 服务端未提交时显示“未提交”，不伪装为正在执行。

### 7.3 失败与重试

- [ ] 主 job 失败时，卡片停在真实失败步骤并保留已完成步骤。
- [ ] 点击重试复用原工程和 job，不新增第二张执行卡。
- [ ] 重试成功后，同一张卡继续到完成并自动收起。
- [ ] 头部和步骤状态图标使用同尺寸圆形槽，并处于同一垂直轴线。
- [ ] 失败叉号使用 SVG，等待圆环与完成、失败圆框尺寸一致。
- [ ] 失败时不在执行卡外、输入框下方或卡片底部重复显示通用失败文案；原始错误只在折叠技术详情中出现。
- [ ] 主 job 超时后，执行卡和产物卡同时显示失败；不存在“视频生成中”的残留状态。

### 7.4 MG

- [ ] 无 MG job 时不显示 MG 进度。
- [ ] MG 仍在执行时，内部主工程可供恢复，但用户可见的视频保持生成中，编辑器入口不可用。
- [ ] 单个 overlay MG 失败或超时时，视频产物显示失败原因和重试入口，并指向具体分镜。
- [ ] full-frame `mg_scene` 失败时显示空白主画面警告，且该镜时长保持不变。
- [ ] MG 全部结束后执行卡进入全部完成；存在失败时保留可见警告和手动重试入口。

## 8. 范围外

- 不为普通聊天回复显示执行卡。
- 不在前端生成或猜测后端步骤。
- 不把执行卡做成第二张确认卡。
- 不改变编导稿、`video_plan`、素材引用或 MG 决策的数据权威。
- 不在本次设计中改造剪辑器或视频产物预览。
