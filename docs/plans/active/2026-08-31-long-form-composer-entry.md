# 长视频与播客统一对话入口设计

> Status: active-plan
> Owner: frontend
> Last verified: 2026-08-31

## 背景与根因

当前新建对话页在主输入框上方单独展示“长视频 / 播客拆条”卡片。这个入口会产生两个并列的创作起点：用户需要先判断应该使用专用入口还是对话输入框，长内容处理也因此看起来像一项独立工具，而不是 Conversation Agent 可以理解的普通创作需求。

专用入口还把“自动给出 Top 5”写成默认承诺，并在视频或链接准备完成后直接发起分析。这把系统内部的展示上限暴露成了用户目标，也会在用户尚未说明要拆片段、整理章节还是按主题筛选时启动高成本任务。

本设计把产品入口收敛到对话输入框。长视频仍可使用专用上传、链接导入、转写和视觉分析链路，但这些差异只存在于内部执行层，不再要求用户先选择一种产品模式。

## 已确认的产品决策

- 新建对话和已有对话共用同一个输入框入口；不再展示独立的长视频 / 播客拆条大卡片。
- 用户可以从输入框添加受支持的视频文件，也可以直接粘贴受支持的视频链接。
- 视频或链接准备完成后只显示为本轮对话的来源附件，不自动启动转写、视觉分析、章节整理或片段推荐。
- 输入框在检测到长视频来源后提示用户先说明处理需求，并提供只负责填入输入框的轻量建议。
- 所有建议都允许用户继续修改；只有用户明确提交需求后，系统才允许启动长内容分析任务。
- 用户表达仍不明确时，Conversation Agent 继续追问，不根据附件类型静默猜测任务。
- 所有用户可见界面、默认指令、进度文案和测试样例都不出现“Top 5”或其他固定数量承诺。
- 结果数量由真实内容质量决定；没有足够合格片段时返回较少结果，不用低质量内容补足数量。
- 视频库针对已有长视频保留上下文操作，但该操作应把素材带入对话并等待用户确认需求，不能绕过对话直接开始分析。

## 交互设计

### 1. 添加来源

用户在对话输入框中完成以下任一操作：

- 点击附件按钮选择视频文件。
- 把视频文件拖入输入区。
- 在输入框中粘贴受支持的视频链接。
- 从视频库选择已有长视频并带入当前对话。

文件上传或链接导入可以先完成，以便形成可引用的来源资产；内容分析任务不得随上传完成自动开始。

### 2. 输入框内确认需求

长视频来源显示为附件卡后，输入框附近提示：

> 你想怎么处理这段内容？

轻量建议使用用户目标语言，不使用内部任务名或结果数量：

- 找出值得发布的片段
- 按指定主题或观点筛选
- 先梳理内容结构

点击建议只把对应自然语言填入输入框并聚焦，不直接执行。用户可以修改建议，也可以完全自行描述需求，例如目标平台、片段用途、主题、人物、时长倾向或需保留的内容。

### 3. 提交与追问

- 来源附件和明确需求一起提交后，前端才发送长内容分析动作。
- 只有附件、没有需求时，不自动创建分析任务；输入框继续提示用户补充目的。
- 用户提交了含糊需求时，Conversation Agent 只追问缺失信息，保持来源附件和当前任务上下文，不创建候选产物。
- 需求明确后才进入来源理解、章节或片段发现流程，并使用普通对话消息持续反馈进度。

### 4. 结果表达

- 结果命名使用“片段建议”“拆条候选”或与用户请求一致的自然语言。
- 不显示固定目标数量，也不使用“已完成 Top 5”一类进度或完成文案。
- 返回结果必须有来源时间范围和原话证据；数量不足不是失败。

## 方案比较

### 方案 A：保留独立入口

优点是能力发现直接，且容易继续复用当前专用上传面板。缺点是长期形成两个主入口，用户需要理解产品内部模式，并且很难自然扩展到章节整理、指定主题筛选等其他长内容需求。因此不采用。

### 方案 B：统一输入框，但上传后弹窗选择用途

优点是可以强制收集结构化需求。缺点是打断对话、增加模式感，也会把开放式创作需求压缩成表单选项。因此不采用。

### 方案 C：统一输入框，使用附件状态和填入式建议

用户始终在同一个对话入口表达目标，专用上传与分析能力保留在内部；建议负责降低首次使用门槛，但不替用户执行。该方案与当前工作台的 AI 原生输入框、建议填入和 Conversation Agent 规则一致，因此采用。

## 状态与数据流

1. 用户添加视频文件、链接或已有视频资产。
2. 前端完成来源上传 / 导入，得到稳定的来源资产 ID。
3. 来源作为待发送附件保留在当前对话草稿中，状态为“已准备，待说明需求”。
4. 用户选择建议或输入自己的目标。
5. 用户发送后，Conversation Agent 判断需求是否足够明确。
6. 不明确时只追问并保留来源；明确时才提交绑定该来源资产的长内容分析动作。
7. 分析产物和后续选择继续存在于同一对话及当前工作对象中。

刷新、切换会话或上传失败时，附件状态不得错误投影成已经开始分析。已经创建的来源资产可以留在资产库复用；未提交的对话草稿是否跨刷新恢复沿用现有附件草稿规则，不在本设计中新增第二套持久化机制。

## 风险与取舍

- 移除独立卡片会降低首页对“长视频拆条”的显性曝光，因此使用输入框附件能力、轻量建议和视频库上下文操作补足发现性。
- 长视频文件的上传方式、大小限制和进度要求与图片 / 文档不同；统一的是用户入口，不是强行共用底层上传实现。
- 链接粘贴可能与普通聊天 URL 冲突。只有在 URL 属于明确支持的来源并经过用户确认时，才把它提升为长视频附件；不支持或不确定的链接继续作为普通文本。
- 需求是否明确属于语义判断，应由 Conversation Agent 的结构化结果负责；前端和固定执行层不得通过关键词词表猜测用户想拆条、总结或筛选。
- 已有代码中可能存在正在进行的对话与视频链路改动。实施前必须通过开发占用门禁核对冲突，不能覆盖其他任务的未提交修改。

## 验证方式

### 前端测试

- 新建对话和已有对话都能通过输入框添加受支持的视频文件。
- 拖入视频不会再显示“请先上传到视频素材库”。
- 粘贴受支持链接后形成来源附件；普通 URL 仍按文本处理。
- 来源准备完成不会调用分析动作，也不会自动创建对话或候选产物。
- 点击三个轻量建议只填入输入框，不发送、不排队。
- 没有明确需求时无法静默启动分析；含糊需求由 Conversation Agent 追问。
- 视频库长视频操作进入对话并保留来源，不直接分析。
- 上传、链接导入失败保留可理解的重试与错误状态。

### 文案与契约检查

- 对生产前端、默认请求、测试 fixtures 和 E2E 断言执行用户可见文案扫描，确认不存在“Top 5”及固定数量承诺。
- 更新工作台设计和 API 文档后运行 `npm --prefix MultiMix-Frontend run docs:check`。
- 运行聊天附件、长视频入口、视频库入口、Conversation Agent 动作和运行时写能力的聚焦测试。
- 使用隔离端口和一次性 SQLite 运行浏览器 E2E，覆盖“添加来源 -> 确认需求 -> 开始分析 -> 返回真实数量结果”，并按工作区规则清理进程和测试库。

## 非目标

- 本设计不改变长视频的转写、视觉理解、候选质量或来源证据规则。
- 本设计不承诺固定的片段数量。
- 本设计不把视频当作普通图片 / 文档上传处理。
- 本设计不移除视频库，也不取消针对已有来源的上下文操作。
- 本设计不在用户确认需求前创建分析任务或生成候选产物。
