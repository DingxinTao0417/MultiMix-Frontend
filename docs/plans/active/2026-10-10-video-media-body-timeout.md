# 视频正文读取超时排查与修复

> Status: active-plan
> Owner: frontend
> Last verified: 2026-10-10

## 背景与证据

用户要求修复现有工程播放超时，并在 Windows 原生浏览器诊断受安全限制后改用可用方式。生产前端为 846c4eed，API deployment 为 392f8e82-42a7-44f5-9918-7ef2f27c0f21。工程断点为 `1555-v4-1419/source1553/director1554/analysis415`；仅复用媒体读取，不修改工程、字幕或数据库，不重做 ASR/人物分析/视频生成。

已确认音频 765203 字节能够读取，视频在 `response.blob()` 正文阶段收到 206 后 60000ms 超时。三次旧记录停在 2MiB，新记录停在 4MiB；不能断言原片某个字节区间损坏。原片总大小 36077615 字节。同一 1MiB 区间经普通 HTTP/1.1、HTTP/2 客户端均完整且哈希相同。

2026-10-10T15:13:30–15:15:30Z 的 Railway 原生只读 HTTP 查询进一步确认五个视频 GET 均有 `txBytes=1048576`，无不足 1MiB 的响应；边缘发送耗时 290–516ms，无 upstreamErrors。这不证明浏览器已收到完整正文。当前根因仍未确认，先观测接收字节和 EOF，不把增大超时作为修复。

## 方案与取舍

1. 先使用原生 Railway 查询及有界、仅内存保存媒体授权的 localhost 传输诊断页，对同一已由产品签发的媒体公开 GET 做 Blob/字节流对照。最多 12 个 1MiB 请求，不自动重试。诊断只记录状态、长度、偏移、耗时、EOF 和字节摘要；不记录 URL、token、文件名、媒体内容或用户信息。它是传输兼容性证据，不冒充产品验收。
2. 确认故障边界后才定稿生产改法。若证实 Blob 完成阶段卡住，改为有界字节读取并统一生成完整 File；若证实接收中断，明确最早故障及已收进度，设计有总期限和次数上限的同文件断点恢复，保留范围、MIME、总大小、权限与文件完整性检查。不得静默拼接未知/损坏/失配响应。
3. 针对确认根因先写失败测试，再最小实现；诊断元数据仅数字/枚举，不能泄露地址或错误正文。预览与导出共用同一正确读取合同，保留原播放壳和确认边界。
4. L1 聚焦测试后跑 L2 消费方回归和仓库要求的检查。使用隔离测试环境，不触碰开发者端口，不新建数据库。
5. 生产发布前整理可审阅的改动、验证、风险和回退点，遵守单写入提交锁与当次推送授权。生产断点只复测现有工程加载、实际播放与必要导出范围；记录真实覆盖与仍未执行的字幕验收。

临时诊断服务器仅监听 127.0.0.1，授权不落盘、不出现在页面地址；结束后关闭服务器、删除内存授权并清理本会话标签。没有证据支持的假设不能被写成根因；如果需改 API，先协调对应持有者并扩大占用后执行。

## 2026-10-10 接收边界结论与最终改法

只读 Chrome 对照共执行两个媒体 GET，均在原片 0–1048575 区间收到 206。Blob+旁路计数收到 636039 字节后于 60011ms 取消，距最后一批数据 524ms；直接字节流收到 544679 字节后于 60024ms 取消，距最后一批数据 663ms。两者均未到 EOF。用户确认 Network 为 No throttling。排除把故障归因于 Blob 完成/转换阶段的假设；本次确认的应用根因为固定“整次请求 60 秒”会取消持续有进度的慢速正文。传输路线变慢的外部原因仍未确认，不能宣称已修复网络本身。

最终改法：使用字节流记录真实接收进度，将现有 60000ms 改作等待响应/正文无进度上限，每批非空数据重置空闲计时；另设不可被进度重置的剩余总期限，整个媒体仍最多 300000ms。保留逐范围 Content-Range、总大小、MIME、Content-Length、完整 File 检查，不添加重试，不延长默认总预算。成功只在 EOF 与完整性通过后发布。失败新增 receivedBytes、expectedBytes、bodyIdleMs 三个纯数字字段；地址、token、媒体内容和原始错误正文不进入诊断。

TDD 红灯：2026-10-10 执行 `npx vitest run editor-engine/vendor/bootstrap.test.ts --testNamePattern "slow response|partial receipt"`，两项按预期失败：80秒持续进度被60000ms取消，部分接收错误事件没有字节/空闲元数据。
